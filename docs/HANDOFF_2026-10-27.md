## 4. 已知的坑（踩过）

- smoke 全量跑要设 `TEMP` 到工作区外，否则 `TemporaryDirectory` 清理报 PermissionError
- `run_code` 的 TS 模板字符串不能出现反引号；Python 补丁脚本里的 `\n` 要用 raw 字符串
- `edit` 前必须 `read`（文件被脚本改动后会提示 stale）
- 大文件批量替换建议用 AST 脚本（本仓 `tests/_smoke_v*.py` 里没有 `__init__.py`，直接 `python 文件` 运行）
- 写补丁脚本时，若原始代码是单行 `except X: pass`，按「替换 pass 所在行」会把 except 头一起删掉；
  批量改写前先扫 handler.lineno == body[0].lineno 的单行块，或整块 AST 重写。
- run_code 的 TS 模板字符串（String.raw）里不能出现反引号；输出 markdown 反引号时，
  在 Python 脚本里写 \x60（Python 解析成反引号），不要写转义反引号。

## 6. v1.77.2（2026-10-28）：删除 graph_adjacency，切断删除路径的整图重建

### 为什么删（实测，线上库副本）

- `graph_adjacency` 是 `relations` 的去规范化镜像，唯一写者是 `GraphStore.add_relation()`；
  生产代码从不调用它（只调 `add_entity_engram_ref()` 写 `graph_engram_refs`）。线上 0 行，
  而 `relations` 有 2120 行、`graph_engram_refs` 990 行 / 396 个 engram。
- 读方 `GraphStore.neighbors()` 因此永远返回空 -> `GraphRetriever` 的 N 跳游走是死代码，
  `DualRouteConfig.graph_relation_hops` 从未生效。
- 唯一会填表的是删除级联里的 `rebuild_from_semantic()`：把 2120 条 relations 展开成 3543 行邻接
  （实测 1.16s）。展开后的图是枢纽图：最高频实体 245 个邻居、146 条 engram 引用；按现有
  `_expand`（每邻居 limit=64、depth decay 1/(1+d)、无度数惩罚），一跳扩展每个锚点新增
  17-217 条候选，足以淹没 RRF 融合。空着「安全」、被重建则洪泛 —— 所以整层移除，而不是回填。

## 7. v1.78.0（2026-10-29）：删除 similar-to 聚类链

### 结论

整条链（similar_to 链接、聚类 gist、情节→语义 profile fact 抽象）删除，不修。

## 9. v1.78.2（2026-10-29）：热重载真正重新加载 bundle

### 怎么发现的

按计划让用户重载插件后核对线上状态，日志尾巴却是：

    [12:16:06] [Core] [INFO] [star.star_manager:1215]: Plugin astrbot_plugin_engram_core (1.78.1) ...
    [hippocampus] loaded: v1.77.0, embedding=hash, llm=rule, engrams=556 ...

metadata 已经是 1.78.1，横幅仍是 v1.77.0；`hippo_meta` 没有 `embedding:fingerprint`，
51 条空向量原样没动，`atoms` 仍为 0 —— v1.77.1 之后的所有改动都没上线。

### 根因

AstrBot `core/star/star_manager.py` 的 `_cleanup_plugin_state()` 只删
`data.plugins.<目录名>.*` 前缀的模块。本插件 `main.py` 把自身目录插入 `sys.path`，
用顶层名导入 `hippocampus` / `handlers` / `page_api`；重载时这些名字不匹配前缀，
继续留在 `sys.modules`。新的 `main.py` 是重新执行的，但它 `from hippocampus import ...`
拿到的是上一次加载的包对象，于是「重载成功」但代码是旧的。

日志佐证：`Removed module` 只有 `data.plugins.astrbot_plugin_engram_core` 和
`data.plugins.astrbot_plugin_engram_core.main` 两条。

### 修复

`main.py` 顶部（`sys.path.insert` 与所有 bundle 导入之前）新增：

- `_PLUGIN_ROOT` / `_BUNDLE_ROOTS`（hippocampus、handlers、page_api、page_api_modules、
  engram_command_registry、engram_core_helpers）
- `_evict_stale_bundles()`：遍历 `sys.modules`，只删「根名在 _BUNDLE_ROOTS 内且
  __file__ 位于本插件目录下」的模块，连同子模块；同名但属于其它目录的模块不动
- `_EVICT_ON_IMPORT = "." in __name__`：AstrBot 用 `data.plugins.<dir>.main` 加载，
  测试用顶层 `main`。只在宿主路径执行，避免测试进程里清掉自己提前导入的模块。
- 导入时执行一次，结果存在 `EVICTED_ON_IMPORT`（便于测试/排障）。

### 验证

`tests/_smoke_v101.py`：

1. 顶层导入时 `_EVICT_ON_IMPORT is False`、`EVICTED_ON_IMPORT == []`
2. 伪造 `hippocampus` / `hippocampus.storage` / `handlers` / `engram_command_registry`

4. 子进程端到端：先导入 `hippocampus` 并打 `STALE_MARKER`，再以

## 11. atom 层在升级库上从未启用（v1.78.3）

§10 里说「atoms 随后开始增长」，实测没有：线上 `atoms` 恒 0，
`_ensure_atom_layer()` 返回 `False`、`atom_store is None`。

根因不是业务逻辑，而是迁移顺序：`AtomStore._init_schema` 把
`CREATE INDEX idx_atoms_expires ON atoms(expires_at)` 放在建表脚本里，
补 `expires_at` 列的 `ALTER TABLE` 在脚本之后。线上 `atoms` 表早于 v1.76.5，
没有该列，于是 `no such column: expires_at` → 构造失败 →
`_ensure_atom_layer` 吞掉异常 → atom 层永久禁用。新库（测试）自然全绿。

修法：`atom_store.py` 改为建表 → 补列 → 建索引（四个索引独立执行）；
`service._ensure_atom_layer` 三个构造失败点补 `_obs_note`，让「能力被禁」可见。
新增 `tests/_smoke_v103.py` 覆盖旧 schema 迁移与 `store_summary` 产原子。

线上库副本验证：修复前 `atom_store is None` / `atoms=0`；修复后 `store_summary()`
写入 2 条 preference 原子。全量 93 个 smoke 全绿。
